# TAOCP 攻克计划 · 算法训练场

教材是 Donald Knuth 的《计算机程序设计艺术》（TAOCP），题库是 LeetCode，
实现语言是 **Rust**。但这个仓库真正的主角不是代码——是**训练本身**。

> **这不是一个"存解法的仓库"，而是一个"让你不再需要仓库"的实验室。**
> 笔记、训练记录、统计数据全部留在这里，作为能力增长的可观测证据。

## 30 秒上手

```bash
cargo run -p lab -- new 49 group_anagrams \
    --title "Group Anagrams / 字母异位词分组" --topic "哈希/排序"   # 导入一道新题
cargo run -p lab -- list                        # 题库 + 复习到期状态
cargo run -p lab -- render p0509 --tier tiny    # ASCII 画出输入长什么样
cargo run -p lab -- diff  p0001                 # 你的暴力解 vs 最优解 正面对决
cargo run -p lab -- bench p0509                 # 看着暴力解爆炸
cargo run -p lab -- run   p0001                 # 完整跑一遍并记入台账
cargo run -p lab -- due                         # 今天该复习哪几道
cargo run -p lab -- stats --write               # 生成 docs/training/stats.md
```

`lab new` 把题目骨架和注册一次做完（以前要手动改两个文件共三处）。
它**只生成骨架**——`brute()` 里是 `todo!()`，那是留给你的。

## 单题闭环（任何一步都不要跳）

```
render  →  手写 brute()  →   diff   →   bench   →  再看 render  →   重构   →   run
看懂输入     只求正确        被击穿     看爆炸      重复显形       自己发明    记账
```

## ⚠️ 先看清楚：仓库里那两道题是「样板题」

`p0001`（Two Sum）和 `p0509`（Fibonacci）的 `brute()` 是**随仓库附带的示范实现，
不是你写的**。它们的作用只有一个：演示这套支架怎么运转。

为了不让它们污染你的训练数据，代码里把它们标成了 `REFERENCE = true`：

- `lab list` 会给它们打上「样板题」标记
- `lab due` **不会**把它们排进复习队列
- 想验证机制是否正常，随便跑 `lab diff p0001` 看看输出即可

> **你的训练从 `lab new` 开始**（或手动复制 `problems/src/_template.rs`）。
> 生成出来的 `brute()` 里写的是 `todo!()` —— 那才是你的起跑线。

## 一次完整的训练（照着敲一遍就懂了）

| # | 你做什么 | 命令 |
|---|---|---|
| 0 | **导入题库**：建题 + 自动注册 | `cargo run -p lab -- new 49 group_anagrams --title "Group Anagrams / 字母异位词分组" --topic "哈希/排序"` |
| 1 | 看输入长什么样（**先别看题解**） | `cargo run -p lab -- render p0049 --tier tiny` |
| 2 | **亲手写 `brute()`** —— 只求正确，不求快 | 编辑器 |
| 3 | 让暴力解被最优解**击穿** | `cargo run -p lab -- diff p0049` |
| 4 | 换种子扩大包围圈 | `cargo run -p lab -- diff p0049 --seed 999 --cases 200` |
| 5 | 看**爆炸点**在哪一档 | `cargo run -p lab -- bench p0049` |
| 6 | 回到第 1 步的图，**自己**发明优化 | 编辑器 |
| 7 | **记账** + 排出下次复习 | `cargo run -p lab -- run p0049 --grade 4` |
| 8 | **写笔记** | `docs/notes/p0049.md` |
| 9 | 第二天回来 | `cargo run -p lab -- due` |

第 3 步红了不要紧 —— 那正是这个系统在干活。**它不告诉你答案，
它只把那个致死的输入原样砸给你。**

### 关于第 8 步：笔记是写给未来的自己的

模板在 `docs/notes/_template.md`，它逼你回答的其实只有两个问题：

1. **我卡在哪** —— 不是"这题怎么做"，而是"我当时那个**错误直觉**是什么"
2. **如果我忘了，先看哪张图** —— 一个**命令**，不是一段推导

第 2 点决定了笔记的价值：**能被一条命令重新激活的笔记才算数。**
抄一遍题解不叫笔记，叫转述。

> 笔记必须你自己写。AI 只做格式检查——它替你写笔记，等于替你消化食物。

## 🔴 给 AI 的约束（本仓库最关键的文件）

`.github/copilot-instructions.md` 与 `.aider.instructions.md` 已经写死以下规则：

- **禁止** AI 代写 `brute()` 的函数体
- **禁止** AI 把最优解留在你的题目文件里 —— 它必须搬进 `problems/src/optimal.rs`
  （否则你写 `brute()` 时等于开卷考试）
- **禁止** AI 说出"用哈希表/双指针/DP"这类**解法关键词**
- **禁止** 安慰式反馈；失败时必须指出**具体输入 / 具体行 / 具体变量**
- AI 只能通过**苏格拉底式反问**引导，一次只问一个问题

> 如果你发现 AI 直接给了你答案，说明约束失效了——去检查上面那两个文件。

## 设计理念

以下是本仓库的设计原点（原始问答，保留在此作为参照）。

问题：我之前一题一题地刷算法面试题，例如leetcode，我顶多是对于算法题进行分类，然后对每一类别的解法进行总结和记忆。感觉有些低效并且一旦停止刷题，就很容易遗忘。那么有了ai agent，尤其是可以自定义agent以及其skill等配置，我可以如何有效地进行算法训练？例如leetcode，

注：我本人没有很好地数学基础。 

答：
实话实说：**靠“分类+总结+记忆”来刷算法题，本质上是在进行“拟像学习（Simulacrum of Learning）”。** 你在使用文科的死记硬背来应对理科的逻辑推导。一旦脱离了题库的特定上下文，或者停止刷题，你的大脑会自动垃圾回收这些没有建立物理逻辑映射的“死知识”。

数学基础薄弱并不是算法学不好的绝症。算法的本质不是高深的微积分，而是“状态机的流转”**与**“内存中数据的搬运”。既然现在有了强大的 AI Agent（如 Aider 或 Cursor），你完全可以打破常规，把 AI 从“给你答案的题库机”改造成“可视化的数学降维打击工具”和“无情的物理压测引擎”。

结合 Mitchell Hashimoto 的“工程化支架（Harness）”思想，以下是为你量身定制的、打破常规的 AI Agent 算法训练体系。

### 一、 核心范式转移：从“解题者”变身为“实验室主管”

不要在 LeetCode 网页端那个枯燥的代码框里刷题。你需要在本地（如 WSL2 环境）建立一个**自动化算法实验室（Algorithm Harness）**。

你的数学基础弱，意味着你很难直接在大脑中完成 $O(N)$ 最优解的数学证明。因此，我们采用“差异化测试（Differential Testing）”的降维打击策略：

1. **你的任务：** 凭直觉，写出一个完全不需要数学技巧、哪怕时间复杂度是 $O(N^3)$ 的暴力解法（Brute Force）。这构成了你的“逻辑基准线”。


2. **Agent 的任务：** 充当黑盒生成器与对抗者。利用 Agent 写出最优解，并自动生成极端边界测试用例，强迫你的暴力解法与最优解进行决斗。



### 二、 针对算法特训的 Agent 技能与规则配置

为了防止 Agent 直接给你正确答案导致“脑萎缩”，你必须在项目根目录创建 `.aider.instructions.md` 或 `.cursorrules` 文件，注入严格的负向约束（Rules）与正向赋能（Skills）。

以下是为你设计的硬核配置文件：

```markdown
# 角色：LeetCode 降维打击教练与对决引擎

## 🔴 Rules (负向约束生死线)
1. **绝对禁令：** 严禁直接向我提供算法的最优解代码，严禁直接告诉我状态转移方程。
2. **反糖衣炮弹：** 当我的代码无法通过测试时，禁止安慰我。直接指出是哪一个具体的边界条件（如数组越界、整型溢出）导致了崩溃。
3. **理解优先：** 我必须手写代码。你只能通过提出“苏格拉底式”的反问来引导我修改[cite: 4]。

## 🟢 Skills (正向赋能)
1. **Skill: 数学降维与可视化 (Visual Decoder)**
   - 触发条件：当我表示看不懂某个算法思路或数学推导时。
   - 动作：禁止使用数学公式向我解释。你必须用纯文本 ASCII 字符画出数组、指针、或者树的内存结构，并一步一步演示数据在每次 `while` 循环中是如何移动的[cite: 4]。
2. **Skill: 对抗性黑盒压测 (Differential Fuzzer)**
   - 触发条件：当我写完一个暴力解法（Brute Force）后。
   - 动作：你需要在后台静默生成该题的最优解，并利用你的逻辑推导能力，生成至少 5 个极端的恶意测试用例（如包含负数、全零、极大图结构）。将这些用例同时喂给我的解法和最优解，如果结果不一致，把导致失败的具体输入数据砸在我的屏幕上[cite: 4, 6]。

```

### 三、 每日 2 小时的前瞻性工作流（头脑风暴实战）

假设你今天要在本地攻克一道极难的动态规划（DP）题。不要看题解，直接按以下流程执行：

* **阶段 1：暴力推演（30分钟）**
完全抛弃 DP 的概念。用你最直观的 DFS（深度优先搜索）甚至多重 `for` 循环把题目解出来。这一步是在你大脑中建立问题的“物理拓扑结构”。


* **阶段 2：召唤 Agent 进行对抗压测（30分钟）**
启动 Aider 或执行自动化脚本，命令 Agent 运行它的黑盒 Fuzzer 技能。当输入规模达到 `N=1000` 时，你的 DFS 必然超时（TLE）。这时候，你通过终端真切地看到了“性能瓶颈”到底卡在了哪一棵递归子树上。


* **阶段 3：可视化降维与重构（60分钟）**
针对超时的部分，向 Agent 提问：*“我的暴力搜索在处理输入 X 时进行了大量重复计算。请使用 ASCII 图画出递归调用树，并向我展示哪些节点的计算是冗余的。”*
当 Agent 画出调用树后，你会直观地看到某些节点被计算了多次。此时 Agent 顺势反问：*“如果我们用一个一维数组把这些红色节点的值存起来，会发生什么？”* —— 此时，你便在没有依赖任何高深数学公式的情况下，依靠视觉和物理直觉，自己发明了“记忆化搜索”和“动态规划”。

**核心总结：** 对于数学基础薄弱的程序员，死记硬背数学公式是无效的。你要利用 AI Agent 不知疲倦的代码编写能力和逻辑推演能力，为你搭建一个"可视化 + 暴力压测"的沙盒。让 AI 去做枯燥的边界测试和公式翻译，你只负责在直观的内存图谱中寻找数据流动的规律。亲手拆解过爆炸现场的人，永远不会忘记炸弹是如何被触发的。
